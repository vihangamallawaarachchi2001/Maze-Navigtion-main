## 1. Introduction and system overview

We built a simulated TurtleBot3 Burger that maps a 3 m × 3 m maze with LiDAR SLAM and localises on the saved
map with AMCL. It reaches destinations clicked in RViz using two interchangeable methods. The first is a
conventional Nav2 stack: Smac 2D (A\*) global planning with a Regulated Pure Pursuit (RPP) controller. The
second is a goal-conditioned **Deep Q-Network** that plans the global route, which the same Nav2 controller
then executes.

Software: ROS 2 Jazzy, Gazebo Harmonic (gz-sim 8.10, DART), SLAM Toolbox, Nav2 1.3 and PyTorch 2.14. These were
installed without root through RoboStack because the lab VM runs Ubuntu 22.04. Figure 1 shows the data flow;
the full diagram is in `docs/architecture.md`.

*[Figure 1: architecture diagram from docs/architecture.md]*

## 2. Maze environment (Task 1)

The maze is generated by `tools/maze_geometry.py` from a list of wall centre-line segments, so the Gazebo world
and the reference geometry map always agree. We measured Figure 1 of the brief pixel by pixel: a solid wall
fills a full grid edge, a dotted guide about 75 %. All horizontal walls matched our transcription. One vertical
wall, x = 1.0 m from y = 0.5 to 1.0 m, had been missed and was added, giving 18 segments. Walls are 0.05 m
thick and 0.30 m high, above the 0.182 m LiDAR plane. On the 0.5 m grid, all 36 cells form one connected
region, with three dead ends.

The Burger model uses ROBOTIS dimensions: wheel radius 0.033 m, track 0.160 m, LiDAR at (−0.032, 0, 0.172) m
above `base_link`, 360 beams, 0.12–3.5 m, 5 Hz. It spawns at (−1.25, −1.25, 0). There the clearance to the
nearest wall surface is 0.225 m, more than the 0.124 m circumscribed radius, so the robot can turn in place.

*[Figure 2: Gazebo overhead view — capture with the GUI: `ros2 launch maze_bringup simulation.launch.py`]*

**Simulation fidelity finding.** Comparing wheel odometry with Gazebo ground truth showed that the robot's
wheels slip in DART during spins. The wheel joints and the DiffDrive odometry agreed exactly, but the body
rotated only 50–90 % of the wheel-implied angle. Changing the step size, friction, caster model, wheel
collision shape and deceleration limits, and trying another physics engine, did not remove the slip. We
therefore publish odometry from Gazebo's OdometryPublisher, i.e. the model pose plus Gaussian noise. DiffDrive
still drives the wheels, and the slipping wheel odometry is kept on `/wheel_odom` as evidence. This is a
disclosed simulation simplification. A side effect is that the `odom` and SLAM `map` frames coincide with the
world frame.

## 3. Mapping and localisation (Task 2)

**SLAM.** SLAM Toolbox (online async) ran while a scripted tour drove the robot through all 36 cells
(55 waypoints, 0.18 m/s, LiDAR safety stop). The tour replaces keyboard teleoperation. The map is built only
from `/scan` and TF. Parameters were derived from the installed Jazzy defaults. Early runs produced rotated
walls. A probe matching scans against the reference geometry showed the scans were consistent with the
odometry pose at their timestamps (yaw offset 0.000 rad even while spinning at 1 rad/s). So the errors came
from false loop closures and over-wide scan-matching searches in this repetitive maze.

We replayed a recorded bag offline to tune the parameters: loop closure off, 0.3 m correlation window,
±0.1 rad coarse angle, higher odometry variance penalties. The final map was then produced in a live run.

| Metric (vs reference geometry) | Original parameters (bag replay) | Final parameters (live) |
|---|---|---|
| Wall cells within 0.10 m of a true wall | 75.9 % | **99.8 %** |
| Median / p95 wall distance | 0.036 / 0.205 m | **0.019 / 0.074 m** |

The planning graph extracted from the SLAM map (36 nodes, 36 edges) is identical to the one from the reference
geometry. The geometry map is kept separately in `maps/reference` and is never presented as a SLAM result.

*[Figure 3: results/analysis/maze_slam_x4.png — the SLAM map]*

**Localisation.** In navigation mode, SLAM is stopped, and map_server plus AMCL take over `map → odom`. AMCL
starts at the spawn pose. Across the 18 comparison trials, its mean final error against ground truth was
0.044–0.049 m.

## 4. Conventional navigation (Task 3a)

- **Global planner:** Nav2 **Smac 2D**, a cost-aware A\* with smoothing. NavFn (Dijkstra) was tried first and
  failed on every route with a turn ("legal potential found but no plan"). That failed run is kept in
  `results/trials_attempt1_navfn.csv`.
- **Controller:** **RPP**, at 0.18 m/s with a 0.10 m lookahead, pivoting at corners. MPPI was too heavy for the VM.
- **Footprints:** planning uses a circle of r = 0.13 m, slightly larger than the true circumscribed radius.
  Local collision checking uses the true polygon outline. The robot is never shrunk.
- **Collision avoidance:** costmaps with live LiDAR obstacles, inflation, RPP's collision check and the
  stock behaviour-tree recoveries (clear costmap, spin, wait, back up).

Tuning was driven by measured failures: RPP falsely predicting collisions near wall ends, lifecycle
heartbeat timeouts under CPU load, and a too-short behaviour-tree server timeout. Each fix is recorded in
`docs/progress.md`.

## 5. Deep Q-learning approach (Task 3b)

**Design (hybrid).** The DQN chooses the **global route**, and the same Nav2 RPP controller executes it. This
is not end-to-end learned motor control.

- **Planning graph:** a 4-connected lattice of corridor centres (0.5 m pitch) built from the SLAM map. Each
  node is refined by up to 8 cm toward the observed corridor centre. A node needs ≥ 0.154 m clearance (robot
  radius + 3 cm). An edge exists only if every 2 cm sample of the straight segment between two nodes is
  known-free with that clearance. Unknown space is blocked.
- **State (80 inputs):** one-hot current node, one-hot goal node, four local move-validity flags and
  normalised indices. The goal is part of the state, so one network serves any clicked goal.
- **Actions:** 4 cardinal moves.
- **Reward:** +100 at the goal, −100 for an invalid move (episode ends), −1 per step, plus Euclidean progress
  shaping. Episodes time out after 60 steps.
- **Learning:** MLP 80 → 256 → 256 → 4, Adam (lr 5·10⁻⁴), Huber loss, replay buffer of 100k, batch 128,
  target network synced every 1000 steps, Double-DQN targets, γ = 0.97, ε 1.0 → 0.05 over 60 % of
  30,000 episodes, seed 42.
- **Held-out split:** 15 % of the 1,260 start/goal pairs are never trained on.

*[Figure 4: results/analysis/dqn_training.png]*

**Training.** 30,000 episodes (162k steps) took 63 minutes on the CPU. Greedy success on held-out pairs passed
90 % around episode 14,000 and reached 100 % by 19,000. In the final greedy evaluation (ε = 0, no learning),
**all 1,071 training and all 189 held-out pairs** reach the goal with the BFS-optimal number of moves. Network
inference takes about 0.5 ms. BFS is used only as the evaluation reference, never for planning. Generalisation
holds within this fixed maze only.

**Deployment.** The `goal_adapter` node attaches the robot's localised pose and the clicked goal to the lattice
through clearance-checked connectors. It runs greedy inference, rejects any route that hits a wall, loops or
times out (there is no classical fallback), densifies the path to 5 cm with headings, and sends it to Nav2
FollowPath. The DQN therefore drives the real simulated robot, not a grid icon.

## 6. Goal execution and efficiency (Tasks 4–5)

Clicks from RViz's **2D Goal Pose** tool go to `/clicked_goal`. `goal_adapter` validates each goal (inside the
map, known-free, ≥ 0.13 m from walls), cancels any running goal, and dispatches it to the selected method. Both
methods then share the map, localisation, controller, limits, goal checker and trial protocol.

**Protocol.** Three goals were chosen from the maze graph: G1 is a short corridor (3 moves), G2 needs turns
(6 moves, 3 turns) and G3 is the farthest cell (18 moves, 13 turns). Each method ran each goal 3 times from the
spawn. Before every trial the robot was teleported back (outside the timed run), AMCL was re-initialised and the
costmaps were cleared.

- **Success:** Nav2 reports success, the **ground-truth** final position is within 0.15 m, and no wall contact.
- **Collision:** a contact event from Gazebo's contact sensor.
- **Near collision:** a LiDAR reading below 0.16 m (counted separately from collisions).
- **Path length:** the sum of odometry displacements.
- **Simulation real-time factor:** 0.32.

| Goal | Method | Success | Collisions | Near-coll. | Sim time (s) | Wall time (s) | Travelled (m) | Planning (s) | Σ\|Δyaw\| (rad) | True final err (m) |
|---|---|---|---|---|---|---|---|---|---|---|
| G1 | Smac+RPP | 3/3 | 0 | 0 | 11.3 ± 0.2 | 35.6 ± 1.5 | 1.42 ± 0.01 | 0.21 ± 0.12 | 1.17 ± 0.10 | 0.088 ± 0.011 |
| G1 | DQN+RPP | 3/3 | 0 | 1 | 9.9 ± 0.2 | 29.8 ± 2.1 | 1.42 ± 0.00 | 0.46 ± 0.11 | 0.69 ± 0.08 | 0.085 ± 0.002 |
| G2 | Smac+RPP | 3/3 | 0 | 11 | 25.4 ± 0.9 | 78.2 ± 2.1 | 2.47 ± 0.05 | 0.23 ± 0.04 | 5.50 ± 0.51 | 0.098 ± 0.025 |
| G2 | DQN+RPP | 3/3 | 0 | 2 | 23.2 ± 1.2 | 78.3 ± 14.0 | 2.68 ± 0.01 | 0.49 ± 0.20 | 5.58 ± 0.24 | 0.108 ± 0.020 |
| G3 | Smac+RPP | 3/3 | 0 | 40 | 80.9 ± 1.6 | 263.0 ± 7.2 | 6.96 ± 0.02 | 0.37 ± 0.06 | 22.29 ± 0.29 | 0.131 ± 0.008 |
| G3 | DQN+RPP | 3/3 | 0 | 9 | 72.9 ± 1.4 | 237.6 ± 25.7 | 7.82 ± 0.03 | 1.38 ± 0.53 | 23.42 ± 0.60 | 0.124 ± 0.004 |

*[Figure 5: results/analysis/comparison.png · Figure 6: results/analysis/routes_G3.png]*

**Interpretation.**
- **Reliability:** both methods reached every goal with no physical collision.
- **Path length:** Smac's smoothed paths are shorter by 8–11 % on the turning routes (G2, G3), because they
  cut the corners that the DQN's cell-centre route takes at 90°.
- **Travel time:** the DQN routes were **faster in simulation time** on all three goals (G3: 72.9 s vs 80.9 s,
  about 10 %). RPP slows down on curves, and Smac's path is a continuous curve, while the DQN route is long
  straight runs joined by in-place pivots.
- **Wall proximity:** the smoothed baseline path ran closer to the walls, with 40 vs 9 near-collision events
  on G3.
- **Planning time:** the DQN's 0.46–1.38 s is almost entirely Python validation of the path clearance. The
  network itself takes about 0.5 ms.
- **Sample size and generality:** with three repeats per cell the differences are consistent but the sample
  is small. We do not claim either method is optimal in general.

The "reference shortest path" (an 8-connected grid path at 0.154 m clearance) is only an approximation. Robots
that cut corners can travel less than it, so a path efficiency above 1 does not mean the robot beat the true
shortest path.

## 7. Challenges and improvements

**Challenges.**
- **No usable machine at the start:** the target VM had no ROS, no sudo access and too little CPU, RAM and disk.
  ROS was installed in user space, and the user resized the VM.
- **Wheel slip in DART:** solved with pose-derived odometry, disclosed above.
- **SLAM distortions:** caused by false loop closures; fixed by replaying the bag offline to tune parameters.
- **Nav2 in 0.45 m corridors:** the planner failure, false collision predictions and lifecycle timeouts
  described in Section 4.
- **Low real-time factor (about 0.3):** every result is therefore reported in both simulation and wall time.

**Improvements.**
- Fix wheel–ground contact so real wheel odometry can be used.
- Use a corner-smoothing post-processor on the DQN route (shorter path, same learned decisions).
- Train with randomised maps so the DQN generalises beyond this maze.
- Test a direct-control DQN (LiDAR sectors → velocity actions).
- Run on a GPU host with real-time factor 1 to cut wall-clock time.
